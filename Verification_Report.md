# RailETA - Complete Verification & Audit Report

This report provides a 100% transparent audit of the RailETA prototype codebase, distinguishing between what is truly functional and what is simulated for demonstration purposes. Use this as a source of truth when creating your presentation.

---

## 🔍 Critical Feature Deep-Dive

### 1. AI/ML Prediction 
- **Is a real ML model trained?** Yes, a real machine learning model is trained and saved.
- **Algorithm Used:** `RandomForestRegressor` from `scikit-learn` (100 estimators, max depth 10).
- **Input Features:** `distance_remaining`, `scheduled_running_time`, `current_delay`, `halt_duration`, `weather_condition`, `congestion_level`.
- **Target Variable:** `actual_running_time` (predicted time taken to reach the next station).
- **Where is it saved?** `backend/ml/eta_model.joblib`.
- **Is the backend using it?** Yes, the API dynamically loads this `.joblib` file and passes user inputs into it to calculate live ETA.
- **Metrics (MAE, RMSE, R²):** MAE = `10.59` minutes, RMSE = `13.56` minutes, R² = `0.9988`.
- **Are metrics calculated from real test data?** **NO**. They are calculated using a 20% test split on *synthetic/mocked historical data* generated by Numpy in `train_model.py`. The ML mechanics are real, but the training data is simulated.

### 2. Dynamic ETA
- **Does an event change model inputs?** Yes. On the `TrainDetails` page, when you change the Delay, Weather, or Congestion sliders, it sends those exact values to the backend.
- **Is the ML model run again?** Yes. The backend calls `model.predict()` on the fly.
- **Does the ETA actually change?** Yes. You can see the `ml_eta_arrival` and `ml_eta_departure` values adjust immediately on the frontend.
- **Does the delay propagate downstream?** Yes. Because the model outputs the running time to the next stop, the backend calculates the arrival time by adding it to the previous departure time. A delay at Stop 2 will cascade down to Stop 5.

### 3. Live Simulation
- **Does train position change?** **NO**. 
- **Does speed/delay change automatically over time?** **NO**. 
- **Implementation Reality:** The `LiveMap` plots static train markers near their origin stations. The `/api/simulation` backend endpoints are completely empty stubs. For the hackathon, the "Live tracking" is a static UI map, while the "Dynamic" aspect requires the user to manually move sliders on the Train Details page.

### 4. Backend
- **Is FastAPI running?** Yes.
- **Endpoints:**
  - `GET /api/trains/`: Returns all trains.
  - `GET /api/trains/{id}`: Returns train info + its full route sequence.
  - `GET /api/trains/{id}/eta?delay=X`: Returns baseline ETA (simple math).
  - `GET /api/trains/{id}/eta/ml?delay=X&weather=Y&congestion=Z`: Runs the Random Forest model and returns AI-adjusted ETA.
- **Example Request/Response:**
  - *Req:* `GET /api/trains/1/eta/ml?delay=15&weather=1&congestion=0`
  - *Res:* `{"train_id": 1, "weather_condition": 1, "eta": [{"station_code": "NDLS", "ml_eta_arrival": "14:30", ...}]}`

### 5. Database
- **Database Used:** SQLite (`raileta.db`).
- **Tables:** `trains` (10 rows), `stations` (15 rows), `routes` (53 rows).
- **Storage:** Standard relational schema using SQLAlchemy ORM. The routes table links a `train_id` to a `station_id` with stop sequences and scheduled times.

### 6. Frontend
- **Dashboard (`/`):** Real functionality. Fetches from SQLite and lists all 10 trains. (Note: "On Time" and "Delayed" top-level metric cards are statically hardcoded).
- **Train Details (`/train/:id`):** Real functionality. Fully wired to the ML API. Sliders control the ML prediction.
- **Live Map (`/map`):** Simulated. Plots static markers on a Leaflet map.
- **Analytics (`/analytics`):** Simulated. Recharts graphs are populated with hardcoded `performanceData` arrays in the React component.
- **Architecture (`/architecture`):** UI Only. A static diagram built with Tailwind.

### 7. Scalability
- **Prototype Implementation:** SQLite (Database), Scikit-Learn (ML), Uvicorn/FastAPI (Backend), React/Vite (Frontend).
- **Proposed Production:** The Architecture page proposes Kafka (streaming), Spark (big data processing), and PostgreSQL (distributed DB), but none of these are actually running in the prototype.
